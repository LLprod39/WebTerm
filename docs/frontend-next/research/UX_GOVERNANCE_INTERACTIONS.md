# Governance / Settings / Projects: инвентарь взаимодействий для UX-прохода

Дата: 2026-09-02. Срез **нового** frontend по текущему исходному коду. Это подготовка к последовательному browser-проходу root, **не результат проверки страниц и не оценка PASS**. Браузер, E2E и внешние сервисы при подготовке не запускались; продуктовый код не изменялся. Старый frontend и история Git не использовались.

Порядок просмотра страниц определяет root. Идентификаторы ниже нужны для записи наблюдений, а не для изменения этого порядка. Метки «дубль», «редкое», «неясно», «сохранение» обозначают кандидатов для проверки в браузере; сами по себе они не предписывают удалять функцию.

Совместимые входы `/settings`, `/settings/users`, `/settings/groups`, `/settings/permissions` перенаправляются соответственно в general и G01–G03. Это не дополнительные страницы. Вкладки G01–G03, P01 и вложенные drawers хранятся локально; G06/S07 используют `?tab=`, G05 — `?view=`, G04 — параметры фильтров URL.

Общие элементы, которые нужно включать в проход **каждой применимой таблицы/формы**:

- `DataTable`: локальный поиск, если передан `searchValue`; кнопка «Очистить поиск»; сортировка только у колонок с `sortValue`; локальная пагинация «Предыдущая страница» / «Следующая страница», номер и диапазон. Футер рисуется и при одной странице. Обычный размер страницы — 15; исключения указаны ниже. Нет общего dropdown видимости колонок, сохранённых фильтров или массового выбора: их не следует искать там, где они не реализованы.
- Строка таблицы сама по себе не всегда кликабельна: вход часто находится в имени и/или отдельной кнопке. Одинаковые действия в двух ячейках отмечены ниже как кандидаты на упрощение.
- Drawer: крестик закрытия, Escape, взаимодействие с подложкой, возврат фокуса. Конкретная защита несохранённых данных зависит от страницы; наличие общего Drawer её не гарантирует.
- ConfirmDialog: «Отмена», подтверждение, блокировка pending; если есть `typedText`, отдельное поле точного названия. Проверить длинные имена и фокус после отмены.
- `JsonDetails`: раскрываемые технические сведения. Это поддерживающий элемент, а не отдельное действие на backend.
- Loading, пустая выборка, пустой результат поиска, ошибка с Retry, mutation feedback, длинные имена и disabled-элементы — отдельные состояния будущего прохода, пока не проверенные этим документом.

## 2. Условия безопасной QA-проверки

Использовать изолированную пару **frontend `http://127.0.0.1:8091` → backend `9001`**, БД `webterm_frontend_qa_20260902`. Эти адреса взяты из текущего QA-контура проекта, но их доступность в этом read-only задании не перепроверялась. `8090/9000` не использовать для экспериментальных изменений.

- Учётные записи QA задаются `frontend/tests/backend/prepare.py`; реквизиты находятся в игнорируемом `frontend/tests/.auth/credentials.json`. Не переносить значения паролей в screenshots/документ. Для проверки отказа — viewer; для staff-функций — QA admin с необходимыми явными feature-разрешениями.
- Пользователи, группы, подключения, пулы и проекты для изменений должны быть собственными временными объектами с узнаваемым префиксом. Смена пароля, деактивация, удаление и отзыв прав — на временном пользователе, а не на текущем операторе прохода. Для проверки наследования нужны два пользователя/две группы с заранее записанными исходными правилами.
- Настройки платформы глобальные. Перед сохранением зафиксировать исходные несекретные значения и восстановить их после проверки. Пустой ввод API-ключа сохраняет старый секрет; для замены нужен специальный тестовый ключ. Старый ключ нельзя восстановить чтением UI.
- Для P01 нужны основной QA-проект и отдельный временный проект, а также временный существующий участник. Создание проекта **сразу активирует его**. UI удаления проекта нет; заранее предусмотреть cleanup через подтверждённый backend/admin-путь либо оставлять только согласованный QA-объект. В конце вернуть исходный active project.
- Для AI CLI доступны отдельные runtime/feature gates. Показ формы без этих prerequisites не означает готовность реального device login. Завершение входа требует тестового аккаунта владельца, runner и активного auth worker. Для проверки полей/пустых состояний не нужен вход в оплаченный аккаунт.
- «Обновить каталог моделей», получение provider billing, CLI «Войти»/«Проверить», удалённый каталог расширений, совместимость и package security scan могут задействовать серверные процессы/внешнюю сеть. Для их выполнения подготовить соответствующий локальный fixture или отдельный тестовый внешний контур; отсутствие такого контура записывать как prerequisite, а не как успешную проверку.
- Для расширений нужны разрешённый тестовый `.wtp`, две версии одного пакета, тестовый источник/JSON-каталог и, если проверяются секреты, отдельная ссылка на тестовый секрет. Включение пакета запускает его runtime; проверка подписи/подписание/аттестация изменяют данные доверия. Retention dry-run сначала; реальная очистка только в выделенном хранилище с известным содержимым.
- Для G04/G05 достаточно безопасного события от собственного QA-пользователя. Активность за 5 минут — выборка зарегистрированных событий, не список всех живых browser sessions. Открытый терминал без новых событий может не попадать в неё.

QA: временный пользователь и группа; отдельно custom и профиль, inherited/allow/deny, изменение собственного тестового пароля с последующим входом только этим тестовым пользователем. Не проверять удаление на seed admin/viewer.

Кандидаты: **дубль** имя/«Настроить»; **неясно** десять профилей без видимой сравнительной матрицы и сброс как обычный пункт dropdown; **сохранение** переход профиль→права→профиль и реакция при закрытии вкладки пароля; **неясно** эффективный результат рядом с несохранённым новым правилом может восприниматься как уже применённый.

QA: два собственных проекта и временный участник; после смены проверить имя active context и списки, затем вернуть исходный проект. Проверить смену проекта из страницы с открытым несохранённым draft как отдельный UX-сценарий; URL может оставаться тем же, поэтому обычный route blocker не является доказательством защиты контекста.

Кандидаты: **редкое** создание и администрирование команды занимают tab-level рядом с частым переключением; **неясно** «Участники» выбирает проект для просмотра команды, не активируя его; active project и selected team могут отличаться; **неясно** роль сохраняется сразу, добавление — кнопкой; **термины** «проект/рабочее пространство/команда/группа доступа» требуют последовательных подписей; **сохранение** закрытие/повторное открытие сохраняет локальный selected/tab/name до размонтирования shell.

## 17. Приоритетные вопросы для browser-прохода

Это вопросы к наблюдаемому UX, не результаты тестов:

1. Видит ли пользователь один ясный основной action на странице и понимает ли, какие действия применяются сразу? В первую очередь G03, P01 roles, plugin grants и AI grant revoke.
2. Не повторяются ли в каждой строке два одинаковых входа (имя + «Настроить/Открыть/Подробнее»), и удобна ли клавиатурная альтернатива после возможного упрощения?
3. Как ведёт себя back, Escape, крестик и переключение вкладки с draft? UserEditor использует native confirm, workspace — свой route guard, остальные формы не наследуют эти защиты автоматически.
4. Понятны ли разные уровни scope: глобальная учётная запись, группа доступа, project role, AI personal/project/workspace defaults, plugin group scope?
5. Показывает ли G04/G05 ровно одну понятную пагинацию для серверной выборки? В source есть и общий table footer, и server controls.
6. Не мешают ли редкие controls (Syslog, trust/sign/attest, package retention, MCP timeouts, CLI weights) обычным задачам? Сохранять доступ к функциям при любой перегруппировке.
7. Различимы ли global AI routing и personal/project model assignments без чтения нескольких длинных пояснений?
8. Понятно ли, что «Общие настройки» — сейчас журналирование, «Рабочее пространство» — персональная раскладка overview, а project switcher — контекст данных?
9. Видна ли причина недоступности и реальный следующий шаг при выключенном CLI runtime, missing LDAP config, empty catalog и неподготовленном provider billing?
10. После успешного save/mutation: закрывается ли правильный dialog, видно ли подтверждение, не остаётся ли stale status, не пропадает ли текст, набранный во время запроса? Проверять это на QA, не делать вывод только из наличия loading spinner.

## 18. Как фиксировать результат следующего прохода

Для каждого G/S/P ID root может записать: открытый route/query; роль/active project; исходное состояние; control и ожидаемое действие; фактическое наблюдение; screenshot/trace; решение «оставить / упростить / перенести / уточнить текст / исправить поведение»; prerequisite для следующей ветви. До этого документа ни одна строка не считается browser-verified.
