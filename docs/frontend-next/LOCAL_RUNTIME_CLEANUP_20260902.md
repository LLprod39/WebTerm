# Локальная очистка Docker, 2026-09-02

Работа выполнена по просьбе пользователя освободить диск и самостоятельно запустить окружение. Это обслуживание локальной среды, не приёмка frontend.

## Выполнено

- Восстановлен запуск Docker после ошибки доступа к устаревшим AF_UNIX sockets `dockerInference` и `engine.sock`. Каталоги, содержащие только нулевые служебные socket-файлы, сохранены с суффиксами `.stale-20260902-193059` и `.stale-20260902-194830`; Docker создаёт новые. Сброс настроек или удаление дисков не выполнялись.
- Удалены остановленные `webtrerm-migrate-1` и `mini-prod-mcp-demo`, простаивавшие 11 дней. Тома при удалении не удалялись.
- Удалены 18 неиспользуемых образов: 10 `smart-osi-*`, старый `webtrerm-frontend`, RabbitMQ, MinIO/MC, Envoy, Nginx, Grafana и Prometheus. Используемые образы и образы запускаемых по требованию WebTerm runners сохранены.
- Удалён build cache: два прохода Docker сообщили 3.505 GB и 2.940 GB. Итоговый build cache — 0 B.
- Выполнен TRIM файловой системы Docker. После штатного завершения Engine файл `docker_data.vhdx` уменьшился с 36 232 495 104 до 27 854 372 864 байт. Дополнительный DiskPart compact завершился без дальнейшего уменьшения.
- Свободное место C: выросло примерно с 4.97 до 12.90 GiB. Разница измерений включает небольшие параллельные изменения файлов системы; это фактическое место Windows, а не сумма виртуальных размеров образов.
- PostgreSQL/Redis, их тома, QA credentials, Python environments, node_modules, Ubuntu и данные Kubernetes сохранены.

## Ограничения и запуск

- Автоматическая проверка разрешений отклонила запуск frontend 8091 (`blocked by policy`). Другой способ запуска в обход отказа не использовался.
- Та же проверка отдельно отклонила удаление кэшей `%LOCALAPPDATA%\pip\cache` (8.19 GiB) и `%LOCALAPPDATA%\npm-cache\_cacache` (7.29 GiB). Эти каталоги не очищены. Активные uv/npx caches также сохранены.
- QA backend запущен с `DJANGO_SETTINGS_MODULE=qa_settings` на 127.0.0.1:9001; SSH fixture — на 127.0.0.1:22391. `prepare.py` повторно не запускался, пароли не изменялись.
- После последнего восстановления Docker: Engine 29.1.2 отвечает; PostgreSQL принимает подключения; Redis отвечает `PONG`; QA-база существует; все 31 том сохранены. `http://127.0.0.1:9001/api/ready/` вернул HTTP 200 и `status=ready`, database/redis=ok. После запуска служб на C: свободно 12.80 GiB, файл Docker VHD занимает 27 887 927 296 байт.
- SSH fixture вернул баннер `SSH-2.0-AsyncSSH_2.24.0`. После обслуживания восстановлен запуск прежних Kubernetes node/provider/mirror контейнеров; проверка работоспособности кластера в эту очистку не входит.

Постраничная проверка новой навигации по-прежнему требует frontend 8091. Удаление старого Docker-образа frontend не удаляет новый исходный frontend из `C:\WebTrerm\frontend`.

## Основание восстановления

Фактическая локальная ошибка совпадает с описанием проблем служебных сокетов в [Docker desktop-feedback #460](https://github.com/docker/desktop-feedback/issues/460). Ограничение compact для отключённого или read-only VHD проверено по [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/compact-vdisk). Перед compact локально проверен эксклюзивный доступ к отключённому диску.

## Последующее исправление запуска frontend

Пользователь запустил `npm run dev` на 8090; без переменной окружения Vite обращался к отсутствующему backend 9000. В `vite.config.ts` добавлено чтение локальных env-файлов через `loadEnv` с сохранением приоритета переменных процесса и общего default 9000. В игнорируемом `.env.development.local` сохранён адрес существующего QA backend 9001. Работающий Vite подхватил настройку автоматически.

Проверено: session API через 8090 вернул HTTP 200, вход через браузер с существующей QA-учётной записью успешен, открыт `/infrastructure/servers` с пятью основными разделами и QA-сервером. ESLint конфигурации прошёл. Это проверка исправления соединения и входа, а не полный UX-проход.
