# «Оператор» — агентный чат WebTrerm

**Статус:** функциональный контур реализован, релизная закалка в работе · **Обновлено:** 2026-07-21 · **Ветка-цель:** test

Полноценный чат уровня GPT, который не просто отвечает, а **работает за оператора со всей платформой**: читает метрики и прогнозы, выполняет команды, пишет и запускает ansible-плейбуки и агентов, забирает отчёты, следит за долгими задачами и сам приходит с новостями.

## 0. Релизная закалка 2026-07-21

Реализовано перед пилотным релизом:

- подтверждение опасных действий теперь требует точного имени сервера, а массовых — слова `FANOUT`; карточка заранее показывает количество и список целей;
- цели массового действия разворачиваются и фиксируются **до** согласия пользователя, поэтому новая машина с подходящим тегом не попадёт в уже подтверждённый запуск;
- согласие на план связано с точными `tool + input` каждого шага; текстовый или устаревший план больше не даёт разрешение на другую операцию;
- действие и активный ход атомарно захватываются в БД, повторный confirm не запускает обработчик второй раз; на сессию действует уникальное ограничение одного активного хода;
- добавлены heartbeat и безопасное завершение потерянного worker-хода; зависшее действие не считается успешным и автоматически не повторяется;
- WebSocket проверяет Origin/Allowed Hosts, некорректный action id и слишком большое сообщение не роняют соединение;
- сырые reasoning-токены модели больше не передаются в интерфейс; результаты мутаций очищаются от секретов перед возвратом в LLM;
- лимиты сообщений, артефактов, ходов и параллельных async-задач считаются на пользователя, а не на отдельный чат;
- каталог tools маршрутизируется по намерению сообщения, чтобы не отправлять модели весь набор схем на каждый простой запрос;
- добавлен opt-in `web_research`: `/web`, Brave Search через фиксированный endpoint, редактирование секретов и внутренних адресов, подписанные result id, блокировка private/link-local/metadata IP, проверка каждого redirect, лимиты ответа и видимые ссылки-источники в сообщении;
- web-контент помечается как недоверенное доказательство и не может разрешать мутации или менять системные инструкции.

Для включения веб-поиска нужно задать `WEB_SEARCH_API_KEY`, применить миграцию и явно выдать пользователю feature `web_research`. Без ключа и разрешения инструмент недоступен.

### Обязательные ворота до внешнего multi-worker production

1. Перенести продолжение долгих ходов в durable queue/lease (Celery/Redis). Текущий heartbeat обеспечивает безопасный fail, но не продолжение после полного падения процесса.
2. Устранить запрещённые зависимости `core_ui -> servers` через provider/registry boundary. Архитектурная проверка всё ещё фиксирует этот контракт как нарушенный.
3. Разрезать крупные файлы `operator_loop.py`, `operator_tools.py`, `ChatPage.tsx` и связанные модули. Это не блокирует внутренний однопользовательский пилот, но блокирует утверждение, что архитектурный gate зелёный.
4. Добавить browser e2e на reconnect, двойное подтверждение, typed-confirm и смену целей между preview/confirm; затем прогнать тест именно в целевой reverse-proxy конфигурации.
5. Для `web.open_result` добавить сетевой egress proxy/firewall или DNS pinning. Проверка адреса и redirect уже закрывает обычный SSRF, но инфраструктурная защита нужна против DNS rebinding в жёсткой production-модели.

## 3. Архитектура

```
ChatPage (React) ⇄ WebSocket /ws/operator/<chat_id>/
                       │ события: token, tool_started, tool_result, plan_update,
                       │ confirm_required, action_update, artifact, usage, turn_done
                       ▼
             OperatorLoop (оркестратор-цикл)
             │  история + сжатие + системный промпт + контекст-чипы
             │  ┌────────────────────────────────┐
             │  │ LLMProvider.stream_chat_tools()│  ← НОВОЕ: native tools
             │  └────────────────────────────────┘
             │        │ tool_use
             ▼        ▼
        ToolRegistry (из AssistantActionSpec + новые read-тулзы)
             │ read → сразу        │ mutate → AssistantAction(pending)
             ▼                     ▼   пауза цикла → confirm → resume
        Платформа: insights API, server_ops, agents, playbooks,
        knowledge, memory, scheduler, sftp, studio
```

### 3.1 Native tool-calling — `LLMProvider.stream_chat_tools()`

Новый метод: `stream_chat_tools(messages, tools, system_prompt, purpose="orchestrator")` → поток событий
`{"type":"text_delta", text} | {"type":"tool_call", id, name, arguments} | {"type":"done", usage}`.

- **Anthropic — основной**: native tools + streaming; `cache_control` на системный промпт и каталог инструментов (каталог большой — кэш обязателен, иначе каждый ход платит за ~40 схем).
- **OpenAI — второй** (тот же интерфейс, function calling).
- Gemini/прочие — fallback через json_mode без стриминга инструментов (честная деградация).
- Схемы tools генерятся из `AssistantActionSpec.input_schema` — один источник правды, ничего не дублируем.

### 3.2 Агентный цикл — `core_ui/services/operator_loop.py`

Состояния хода: `thinking → tool_running → awaiting_confirm → resuming → done|failed|limit`.

- **Read-инструменты** выполняются немедленно, результат → в контекст, цикл продолжается.
- **Мутирующий инструмент** ⇒ `AssistantAction(status=requires_confirmation)`, ход **паркуется**: LLM-сообщения и pending tool-call сериализуются в новую модель `ChatTurnState`. Фронт показывает карточку. `confirm` → действие выполняется, цикл **резюмится** с результатом; `cancel` → в контекст уходит «пользователь отклонил» — LLM предлагает альтернативу, а не молчит.
- **Лимиты:** ≤ 12 итераций/ход, бюджет токенов/ход, таймаут инструмента 60 с; на превышении — честное сообщение («упёрся в лимит, вот что успел»).
- **Долгие инструменты** (агент, плейбук) возвращают `{async: true, run_id}` мгновенно — ход завершается «слежу за run #N», продолжение в §6.3.
- **Сжатие истории:** после ~20 сообщений старые ходы сворачиваются в summary-сообщение (паттерн памяти серверов); результаты инструментов старше 2 ходов урезаются до превью.

### 3.3 Данные (миграция core_ui)

- `ChatTurnState` — session FK, llm_messages JSON, pending_action FK, status, счётчики итераций/токенов.
- `ChatArtifact` — session FK, message FK, kind (`ansible`/`script`/`report`/`chart`), title, content, version, saved_playbook FK nullable.
- `AssistantAction` +поля: `undo_payload` JSON, `dry_run_preview` JSON, `blast_radius` JSON, `async_run_ref`.
- `ChatSession` +поля: `kind` (`manual`/`duty`/`incident`), `pinned_context` JSON (чипы @server и т.п.), `total_usage` JSON.

## 5. Killer-фичи (то, что делает «вау»)

### 5.1 План-режим
Системный промпт: если задача требует >2 мутаций — сначала **план-чеклист** (спец-блок в сообщении), одна кнопка «Выполнять». Дальше цикл идёт по шагам, каждый шаг в чате отмечается ✅/❌ живьём (`plan_update` события), можно остановить в любой момент. Одно подтверждение на план вместо десяти кликов — но destructive-шаги всё равно подтверждаются отдельно.

### 5.2 Slash-команды и @-упоминания
`@db-01` — привязать сообщение к серверу (autocomplete по доступным), чип ложится в `pinned_context` и едет в системный промпт. `/fleet`, `/forecasts`, `/run <cmd>`, `/briefing` — мгновенные шаблоны без набора текста. Парсинг на клиенте → структурные подсказки в ход.

### 5.3 Dry-run + «радиус поражения»
Каждая карточка подтверждения показывает: точную команду/diff, **сколько и какие серверы затронет** (`blast_radius`), прод-теги красным, и где возможно — результат сухого прогона (ansible `--check`, `run_command` с echo-превью). Оператор подтверждает не «доверие», а конкретику.

### 5.4 Фан-аут по флоту с матрицей
«Обнови nginx на всех prod» → инструмент разворачивает цель (теги/группа/список) → карточка с перечнем → после подтверждения выполняет с ограничением параллельности → в чат падает **живая матрица**: сервер × статус × время × краткий вывод, ошибки раскрываются. Итог: «14 ок, 2 ошибки — разобрать?»

### 5.5 «Сохранить как runbook»
Кнопка на успешном ходе/плане: цепочка выполненных шагов конвертится в Playbook (runbook-kind) с параметризацией сервера. Следующий раз — одна команда `/runbook wal-cleanup @db-02`. Чат **накапливает опыт команды**, а не только болтает.

### 5.6 Undo последнего действия
Мутирующие инструменты по возможности декларируют обратную операцию (`undo_payload`): установил пакет → команда удаления; записал файл → сохранили предыдущую версию; включил unit → выключить. В чате кнопка «Откатить» (создаёт обратное действие с обычным подтверждением). Там, где отката нет (rm), карточка честно пишет «необратимо» ещё ДО подтверждения.

### 5.7 Инлайн-графики и таблицы
Ответы не только текстом: сообщение может нести `metadata.chart`/`metadata.table` → фронт рендерит спарклайны/мини-графики (готовый `Sparkline`) и таблицы. «Покажи память db-01 за неделю» → график прямо в чате, с прогнозной пунктирной линией из `ServerPrediction`.

### 5.8 Верстак артефактов
Сгенерированный ansible/скрипт — не кусок текста, а **артефакт** в боковой панели: подсветка, редактирование, версии, кнопки «Сохранить как Playbook» / «Запустить (check)» / «Запустить». Итерации «поправь строку 12» обновляют версию артефакта, а не плодят простыни в чате.

### 5.9 Проактивный «Дежурный»
Выделенная сессия `kind=duty`: утренний брифинг (дифф за ночь: новые прогнозы/алерты/раны — через LLM-сводку), сообщения при критических событиях («на web-01 сработал прогноз, я посмотрел логи — вот что вижу»). Механика: цикл в `run_monitor` + `report_delivery` в чат. Отключаемо per-user.

### 5.10 Граунд на памяти серверов
Перед мутацией на сервере цикл автоматически подмешивает карточку памяти: «⚠ Я помню: на этом сервере в мае падал nginx при reload — в прошлый раз помог restart». Прошлый опыт платформы работает в каждом ходе.

### 5.11 Стоимость на виду
Чип на ходе: токены и $ (usage из `done`-события, курсы уже есть в api_usage). Сумма по сессии в шапке. Никаких сюрпризов по счетам.

### 5.12 «Разобрать в чате» отовсюду
Кнопки на алертах, прогнозах, AI-вердиктах, watcher-драфтах, ранах агентов → открывают чат `kind=incident` с уже собранным контекстом (сервер, объект, метрики окна, свежие логи). Ноль копипасты.

## 6. Фазы реализации

### Ф1 — Ядро: tool-calling + цикл + стриминг (4–5 дн)
`app/core/llm_tools.py` (stream_chat_tools: Anthropic → OpenAI → json-fallback), `core_ui/services/operator_loop.py`, `ChatTurnState`, WS-консьюмер `core_ui/consumers/operator_chat.py`, конвертер спек → tools, пауза/резюм на подтверждении, сжатие истории, лимиты.
**Готово, когда:** в старом UI чата ход с 2 read-инструментами стримится токенами; мутация паркуется и резюмится после confirm; тесты цикла на мокнутом LLM зелёные.

### Ф2 — Каталог инструментов (3–4 дн)
Все read-тулзы §4 (тонкие обёртки над существующими сервисами), `run_command` через execution_policy, playbooks (create/run/check/report), write_file c diff, schedule_agent, resolve_alert/ack_draft. Регистрация через существующий `register_action`.
**Готово:** сценарий «что с флотом → выполни df на db-01 → покажи отчёт последнего рана» проходит в чате без рук.

### Ф3 — Долгие задачи (2–3 дн)
Async-инструменты: мгновенный `{run_id}`, карточка «в работе» с live-прогрессом (events ранов уже стримятся), **автопродолжение хода по завершении** (signal/worker: run завершился → цикл резюмится → LLM читает отчёт → резюме в чат).
**Готово:** «запусти агента X и расскажи, что вышло» работает end-to-end без участия оператора.

### Ф4 — UX уровня GPT (4–5 дн)
Редизайн ChatPage: стриминговый markdown, сворачиваемый таймлайн шагов, карточки подтверждения (команда/diff/blast radius/undo-метка), верстак артефактов (§5.8), slash/@ (§5.2), план-режим UI (§5.1), инлайн-графики (§5.7), чип стоимости (§5.11), сессии/переименование. Включить `CHAT_NAV_READY`.
**Готово:** сценарий «пожар» из §1 воспроизводится целиком и выглядит как в описании.

### Ф5 — Сила: фан-аут, dry-run, undo, runbooks (3–4 дн)
`run_fanout` с матрицей (§5.4), dry-run/blast radius в карточках (§5.3), undo_payload у ключевых инструментов (§5.6), save_runbook + `/runbook` (§5.5).
**Готово:** «обнови пакет на всех stg» — матрица; успешную цепочку можно сохранить и переиграть runbook'ом.

### Ф6 — Проактивность (2–3 дн)
Дежурная сессия + брифинг (§5.9), «Разобрать в чате» на алертах/прогнозах/ранах (§5.12), расписания фразой (schedule_agent + доставка отчёта в чат).
**Готово:** утренний брифинг приходит сам; с страницы мониторинга инцидент открывается в чате с контекстом.

### Ф7 — Безопасность и закалка (2–3 дн)
Typed-confirm для destructive (имя сервера руками), политика per-профиль (pilot_user — только read+confirm-mutate), rate-limit ходов, полный аудит, e2e-тесты сценариев §1, нагрузочный тест длинной сессии, docs.
**Готово:** security-review чек-лист пройден; 0 инструментов мимо аудита/редакции.

**Итого: ~3.5–4 недели.** Вертикальный срез «живой рабочий чат» — после Ф1+Ф2 (~неделя+).

## 7. Риски и деградации

- **Tool-calling у трёх провайдеров разный** → Anthropic первым классом, OpenAI вторым, остальные json-fallback. Интерфейс событий один.
- **Токены**: каталог инструментов большой → prompt-кэш (Anthropic cache_control), сжатие истории с Ф1, урезание старых tool-результатов.
- **Опасные команды**: execution_policy уже классифицирует риск команд — карточка наследует категорию; ai_read_only непереопределяем из чата.
- **Зависший async-ран** → таймаут слежения + ручное «проверь ран #N».
- **Параллельные подтверждения** — один pending-ход на сессию (второе сообщение до резюма — в очередь).
