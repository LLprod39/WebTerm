# Спецификация нод Studio Pipeline (WebTrerm)

Данный документ описывает логику работы, входные и выходные параметры всех доступных узлов (нод) в Studio Pipeline.

---

## Общие принципы работы

### 1. Интерполяция переменных (Templating)
Большинство текстовых полей поддерживают вставку значений из предыдущих шагов с помощью синтаксиса `{variable_name}`.
Доступные переменные:
- `{run_id}`: ID текущего запуска.
- `{pipeline_name}`: Название пайплайна.
- `{trigger_type}`: Тип триггера (webhook, cron, manual).
- `{node_id}` или `{node_id_output}`: Финальный текстовый отчет узла с указанным ID.
- `{node_id_error}`: Текст ошибки узла (если есть).
- `{node_id_status}`: Статус завершения узла (`completed`, `failed`).

### 2. Контекст исполнения
Каждый узел при выполнении получает «обогащенный контекст» (enriched context), который включает все выходные данные всех ранее выполненных узлов.

### 3. Статусы узлов
- `completed`: Узел успешно выполнил свою задачу.
- `failed`: Произошла ошибка (остановка пайплайна, если не предусмотрена обработка).
- `skipped`: Узел был пропущен (например, из-за условия).
- `awaiting_approval`: Узел ожидает действия человека.

## Группа: Агенты (agent/*)

### 1. agent/react (AI Агент)
**Логика:** Полноценный автономный агент, работающий по циклу ReAct (Reasoning + Acting). Способен самостоятельно выбирать инструменты для достижения цели.

- **Входные данные:**
    - `goal` (string): Цель агента. Поддерживает шаблоны.
    - `agent_config_id` (ID): (Опционально) Ссылка на готовую конфигурацию агента.
    - `server_ids` (list): Список серверов, на которых разрешено работать.
    - `mcp_server_ids` (list): Подключенные MCP-серверы.
    - `skill_slugs` (list): Список подключенных навыков (skills).
    - `model` (string): Используемая LLM модель (по умолчанию `gemini-2.0-flash-exp`).
    - `max_iterations` (int): Максимальное количество шагов в цикле (обычно 10-20).
- **Работа:** Агент получает контекст сервера (через Memory Card), доступные инструменты (SSH, MCP) и инструкции. Выполняет команды, анализирует результат и продолжает до достижения цели или лимита итераций.
- **Выход:** Текстовый отчет о проделанной работе в `output`.

### 2. agent/multi (Мульти-агент)
**Логика:** Оркестрация группы специализированных агентов для решения сложной задачи.

- **Работа:** Аналогичен `agent/react`, но использует `MultiAgentEngine` для распараллеливания или делегирования подзадач внутри одного узла.
- **Выход:** Сводный отчет по всем подзадачам.

### 3. agent/ssh_cmd (Прямая SSH команда)
**Логика:** Выполнение конкретной команды на сервере по SSH без участия ИИ.

- **Входные данные:**
    - `server_id` (ID): Целевой сервер.
    - `command` (string): Команда для выполнения (поддерживает `{template}`).
    - `preflight_commands` (list): (Опционально) Команды проверки перед основной задачей.
    - `verification_commands` (list): (Опционально) Команды проверки результата.
- **Работа:** Прямое подключение через `asyncssh`. Если команда не задана, но указан ИИ-агент, узел может автоматически переключиться в режим `agent/react`.
- **Выход:** Объединенный `stdout` и `stderr` команды.

### 4. agent/llm_query (Прямой запрос к LLM)
**Логика:** «Чистое» рассуждение или анализ текста без доступа к серверам.

- **Входные данные:**
    - `prompt` (string): Запрос к модели.
    - `system_prompt` (string): Системная роль.
    - `include_all_outputs` (bool): Если True, в контекст будет вставлен вывод всех предыдущих узлов.
- **Работа:** Отправляет запрос выбранному провайдеру (Gemini, OpenAI и т.д.). Полезно для суммаризации, принятия решений или генерации текста.
- **Выход:** Текст ответа LLM.

### 5. agent/mcp_call (Вызов MCP инструмента)
**Логика:** Прямой вызов конкретной функции (инструмента) с MCP-сервера.

- **Входные данные:**
    - `mcp_server_id`: ID MCP сервера из пула.
    - `tool_name`: Название инструмента.
    - `arguments_text` (JSON): Параметры вызова (поддерживают шаблоны).
- **Работа:** Узел вызывает инструмент напрямую через MCP клиент. Проверяется соответствие политикам безопасности (Skill Policies).
- **Выход:** Результат работы инструмента (JSON или текст).

## Группа: Логика (logic/*)

### 1. logic/condition (Условие)
**Логика:** Разветвление пайплайна на основе результата предыдущего узла.

- **Входные данные:**
    - `source_node_id`: Узел, чей вывод проверяем.
    - `check_type`: Тип проверки (`contains`, `not_contains`, `status_ok`, `status_failed`, `always_true`).
    - `check_value`: Значение для поиска.
- **Работа:** Если условие истинно, узел завершается со статусом `completed` и выполнение идет по ветке "success". Если ложно — узел пропускается (`skipped`).
- **Выход:** Статус прохождения проверки.

### 2. logic/wait (Ожидание)
**Логика:** Приостановка выполнения пайплайна на заданное время.

- **Входные данные:**
    - `wait_minutes` (float): Время ожидания (от 0.1 мин до 24 часов).
- **Работа:** Пайплайн «засыпает». Периодически проверяется, не был ли запуск остановлен пользователем.
- **Выход:** Подтверждение завершения ожидания.

### 4. logic/human_approval (Одобрение человеком)
**Логика:** Пауза до тех пор, пока ответственный сотрудник не нажмет «Одобрить» или «Отклонить».

- **Входные данные:**
    - `message` (template): Сообщение для уведомления.
    - `to_email` / `tg_chat_id`: Куда отправить запрос.
    - `timeout_minutes`: Время ожидания решения (по умолчанию 120 мин).
- **Работа:** Генерирует одноразовый токен. Отправляет Email и/или Telegram сообщение с кнопками/ссылками. Если нажато «Одобрить» — пайплайн идет дальше. Если «Отклонить» — узел считается `failed`.
- **Выход:** Текст решения или причина отказа.

### 5. logic/telegram_input (Запрос текста в Telegram)
**Логика:** Пауза до тех пор, пока оператор не пришлет текстовый ответ в Telegram.

- **Входные данные:**
    - `message` (template): Текст запроса.
    - `bot_token` / `chat_id`: Настройки бота.
    - `timeout_minutes`: Время ожидания ответа.
- **Работа:** Бот отправляет сообщение с функцией `force_reply`. Пайплайн переходит в состояние ожидания (hibernating) и опрашивает Telegram API на предмет ответа на конкретное сообщение.
- **Выход:** Текст ответа оператора.

### 6. logic/parallel (Параллельное разветвление)
**Логика:** Точка входа для запуска нескольких веток одновременно.
- **Работа:** Узел служит маркером в графе. Все исходящие из него ветки будут запущены `PipelineExecutor` параллельно (в отдельных asyncio задачах).

### 7. logic/merge (Объединение)
**Логика:** Ожидание завершения нескольких параллельных веток.

- **Режимы:**
    - `all`: Ждать завершения всех входящих узлов.
    - `any`: Продолжить, как только завершится хотя бы один.

## Группа: Вывод (output/*)

### 1. output/report (Генерация отчета)
**Логика:** Сбор результатов работы пайплайна в финальный Markdown документ.

- **Входные данные:**
    - `template` (Markdown): Шаблон отчета. Если пусто — генерируется автоматически список всех нод и их выводов.
- **Работа:** Сохраняет результат в поле `summary` объекта `PipelineRun`. Этот отчет отображается в интерфейсе Studio.

### 2. output/webhook (Вебхук)
**Логика:** Отправка результатов работы на внешний URL.

- **Входные данные:**
    - `url`: Куда слать POST-запрос.
    - `extra_payload` (JSON): Дополнительные поля.
- **Работа:** Отправляет JSON, содержащий весь `context` запуска и выводы всех нод.

### 3. output/email (Email уведомление)
**Логика:** Отправка отчета на электронную почту.

- **Входные данные:**
    - `to_email`: Получатель.
    - `subject` / `body` (templates): Тема и текст письма.
- **Работа:** Использует SMTP настройки (глобальные или из ноды).

### 4. output/telegram (Telegram уведомление)
**Логика:** Отправка сообщения в Telegram бот.

- **Входные данные:**
    - `bot_token` / `chat_id`: Настройки бота.
    - `message` (template): Текст сообщения.
- **Работа:** Поддерживает форматирование Markdown/HTML. Позволяет быстро узнать статус выполнения пайплайна.
